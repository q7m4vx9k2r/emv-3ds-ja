### 5.9.13 ACS RRes Message Error Handling—03-3RI

The ACS processes the validation of the RRes message or Error Message as follows:

- For a message that cannot be recognised, the ACS:

o Returns to the DS an Error Message (as defined in Section A.9) with Error Component = A and Error Code = 101.

- For an RRes message, the ACS Validates the RRes message (as defined in Table B.9 and Section 5.1.7):

o If any data element present fails validation, the ACS:

− Returns to the DS an Error Message (as defined in Section A.9) with Error Component = A and Error Code = 203.

o If any required data elements are missing, the ACS:

− Returns to the DS an Error Message (as defined in Section A.9) with Error Component = A and Error Code = 201.

o Otherwise, the message is not in error.

### 5.10 UTC Date and Time

This section provides requirements for the handling of UTC date and time by the 3DS components.

Seq 5.114 [Req 416] The maximum desynchronisation with UTC time for the 3DS Server, DS and ACS shall be less than 15 minutes when providing or verifying the UTC date and time data elements.

The DS shall respond to the 3DS Server with an Error Message (as defined in Section A.9) with Error Component = D and Error Code = 203 if the SDK Signature Timestamp or Purchase Date & Time data elements are received with a UTC time difference greater than 30 minutes.

Seq 5.115 [Req 417] The ACS may respond to the DS with an Error Message (as defined in Section A.9) with Error Component = A and Error Code = 203 if the SDK Signature Timestamp or Purchase Date & Time data elements are received with a UTC time difference greater than 30 minutes.
