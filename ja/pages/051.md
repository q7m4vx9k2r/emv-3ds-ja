#### 手順1：カード会員

カード会員は、3DS Requestor Appを使って3DS Requestorと対話し、該当する業務ロジックを確認する。例えば、消費者端末上の3DS Requestor Appを使って電子商取引による購入を行う。

#### 手順2：3DS Requestor App

3DS Requestor Environment（2.1.1節で概説）によっては、追加情報を取得してもよい。例えば、支払認証のための支払情報やショッピングカート情報が該当する。

3DS Serverは、3DS Requestor Environmentを通じて、次の情報を3DS Requestor Appに提供する。

- 端末情報の暗号化に使う鍵を識別するDirectory Server ID値（決済システムのRID）。
- CReq／CResで使用するMessage Version Number。

3DS Serverは、次を実施しなければならない。

**Seq 3.1 [Req 11]** ISO 7812で定義されるBINと、任意のその他のCardholder Account Informationに基づき、認証取引の送信先となるDSを判定する。

**Seq 3.2 [Req 419]** PResから取得したACS Protocol VersionsおよびDS Protocol Versionsのプロトコルバージョン一覧と、3DS SDKが対応するプロトコルバージョンを使い、共通して対応する最高のMessage Version Numberを設定する。

3DS Requestor Appは、3-D Secureカード会員認証を開始するために3DS SDKを起動する。次の情報を3DS SDKに渡す。

- Directory Server ID値（決済システムのRID）。
- Message Version（3DS Requestor Environmentから取得）。

また、次の情報を取得する。

- SDK Transaction ID
- SDK App ID
- Device Information
- Protocol Version（この取引で3DS SDKが使用するバージョン）

注：Message Versionがnullの場合、3DS SDKは対応する最高のプロトコルバージョンを使用する。値がある場合はそのバージョンを使用する（3DS SDKが対応していることが前提）。対応していなければエラーとなる。

注：適用される3DS SDK仕様に記載するとおり、3DS SDKはDS公開鍵を使ってDevice Informationを暗号化する。この鍵は、3DS SDKの起動時に渡されるDirectory Server IDに基づいて識別される。

#### 手順3：3DS SDK

3DS SDKは、AReqに必要なデータを返す。

#### 手順4：3DS Requestor Environment

3DS Requestor Environmentは、3DS Serverが組み立てるAReqの情報を収集する責任を持つ。
