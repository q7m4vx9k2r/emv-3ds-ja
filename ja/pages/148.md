### 5.1.7 メッセージ内容の検証

メッセージの検証時には、次の要件を適用する。

**Seq 5.30 [Req 204]** 表A.1で定義するとおり、受信したMessage TypeのすべてのRequiredフィールドが存在しなければならない。

**Seq 5.31 [Req 205]** 表A.1で定義する存在条件を送信元構成要素が満たすと判断した場合、受信したMessage TypeのすべてのConditionalフィールドが存在しなければならない。

**Seq 5.32 [Req 206]** Message Typeに含まれるRequired、Conditional、Optionalフィールドは、表A.1で指定する形式と長さの基準を満たさなければならない。

**Seq 5.33 [Req 309]** 明示的な注記がない限り、条件付き任意または任意のフィールドが空またはnullとして送信された場合、受信側は、適切なError ComponentとError Code = 203を持つErrorメッセージ（A.9節で定義）を返さなければならない。

例：DSがACSから、Message Type、Device Channel、Message Categoryについて表A.1で指定されているが条件を満たさない、空の条件付き任意データ要素を持つAResを受信する。例えば`acsChallengeMandated = ""`かつ`transStatus = Y`の場合である。DSはAResの内容を検証し、ACSにエラーを返す。3DS ServerにはAResまたはErrorを返すことができる。

メッセージの検証基準はMessage Typeフィールドに基づき、次のとおり適用する。

**Seq 5.34 [Req 207]** 将来のプロトコルバージョンに対応するため、実装は厳格な検証を行うJSON内容パーサを使用、またはそのように設定してはならない。構文が正しく、表A.1で定義するMessage Typeの検証基準を満たす場合、メッセージを有効とみなさなければならない。

**Seq 5.35 [Req 208]** 受信したMessage Typeの内容検証が、表A.1の基準を満たさない場合、エラーとして扱わなければならない。

**Seq 5.36 [Req 209]** Message Type、Device Channel、Message Categoryについて指定されていない追加データ要素を受信しても、それ以外の検証に合格する場合、メッセージを有効とみなさなければならない。

追加データ要素（データ拡張を除く）について、受信側3DS構成要素は次のいずれかを実施しなければならない。

- 追加データ要素を無視し、フロー内の次の3DS構成要素へ送らない。
- 次ページに示す形式確認を行う。
