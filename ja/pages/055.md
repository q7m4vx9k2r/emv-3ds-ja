**Seq 3.29 [Req 24]** [Req 23]で確立したセキュアな接続を使って、AReqをACSに送信する。

ACSからAResを受信しない場合（5.5節で定義）、DSは[Req 235]で指定するメッセージを3DS Serverに返し、処理を終了する。

#### 手順7：ACS

ACSは、次を実施しなければならない。

**Seq 3.30 [Req 25]** DSからAReqを受信し、5.9.2節で定義するとおりに検証する。

メッセージにエラーがある場合、ACSは処理を終了する。

**Seq 3.31 [Req 26]** Decoupled Authenticationとして処理する取引でない限り、消費者端末に対応しているかを確認する。

対応していない場合、ACSはDSに、Transaction Status = U、Transaction Status Reasonコード = 03のAResを返し、処理を終了する。

**Seq 3.32 [Req 386]** Device Informationのデータ要素がData Version Numberに対応しているかを確認する。

Device Informationのデータ要素がData Versionに一致しない場合、ACSはErrorメッセージ（Error Code = 203）を返すか、取引処理を続行する。

注：ACSはAReqで受信したDevice Informationを使い、端末の識別、取引リスクの評価、認証を完了できるかの判定を行う。

注：Decoupled Authenticationを使用する場合、ACSがカード会員を認証する代替手段を持つなら、取引を開始した消費者端末に対応する必要はない。

**Seq 3.33 [Req 318]** ACSは、フリクションレス取引の一部としてカード会員との対話を開始してはならない。カード会員との対話は、チャレンジフローの一部として実施しなければならない。

**Seq 3.34 [Req 27]** ACS Transaction IDを生成する。

**Seq 3.35 [Req 28]** AReqのCardholder Account Numberを使い、そのカード会員の認証が利用可能か、または完了可能かを判定する。

Cardholder Account Numberの認証が利用できない場合、ACSはDSに、個々のDSが定義する適切な応答をTransaction StatusとTransaction Status Reasonコードに設定したARes（表B.2で定義）を返し、処理を終了する。

ACSには、次の実施を推奨する。

**Seq 3.36 [Req 29]** [Req 30]で定義する取引の処置を評価する際、AReqで受信した3DS Requestor Challenge Indicator、3DS Requestor Authentication Indicator、および3DS Requestor Decoupled Request Indicatorの値を使用する。
