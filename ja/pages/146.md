**Seq 5.9 [Req 191]** CReq／CResのContent-Typeヘッダー要件は次のとおりである。

- アプリ方式のCReq／CRes：Content-Typeに`application/jose`を含め、charsetとしてUTF-8を含めなければならない。例：`Content-Type: application/jose; charset = UTF-8`。
- ブラウザ方式のCReq：Content-Typeに`application/x-www-form-urlencoded`を含めなければならない。例：`Content-Type: application/x-www-form-urlencoded`。
- ブラウザ方式のCRes：Content-Typeに`text/html`を含め、charsetとしてUTF-8を含めなければならない。例：`Content-Type: text/html; charset = UTF-8`。

HTTPヘッダーには、3-D Secureメッセージを支援する追加情報も含める。

**Seq 5.10 [Req 468]** AReq、CReq、RReq、OReq、PReqでは、送信する3DS構成要素は、表A.29で定義するとおり、HTTPヘッダーのX-Request-IDを使って自身のTransaction IDを含めなければならない。

**Seq 5.11 [Req 469]** ARes、CRes、RRes、ORes、PResでは、送信する3DS構成要素は、表A.29で定義するとおり、X-Response-IDを使って自身のTransaction IDを含め、X-Request-IDを使って要求メッセージ内（HTTPヘッダー内ではない）で受信した送信元のTransaction IDを含めなければならない。

### 5.1.3 Base64／Base64urlエンコード

3-D Secure仕様では、附属書Aで定義する特定のメッセージ要素の内容の整形に一貫性を持たせるため、Base64およびBase64urlエンコードを使用する。

**Seq 5.12 [Req 192]** エンコード方法は、Base64についてIETF RFC 2045、Base64urlについてIETF RFC 7515に従わなければならない。

**Seq 5.13 [Req 193]** Base64復号ソフトウェアは、Base64でエンコードされたデータ内の空白文字（復帰や行末など）を無視し、それらの存在をエラーとして扱ってはならない。

### 5.1.4 プロトコルとメッセージのバージョン番号

注：Protocol Version NumberおよびMessage Version Numberは、major.minor.patch形式（例えば2.3.1）である。

**Seq 5.14 [Req 195]** EMV Specification Bulletin 255で有効とされていないMessage Version Numberは、すべてエラーとして返さなければならない。3-D Secure構成要素は、適切なError ComponentとError Code = 102を持つErrorメッセージ（A.9節で定義）を返さなければならない。
