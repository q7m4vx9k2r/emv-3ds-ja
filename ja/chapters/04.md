## 4 EMV 3-D Secureのユーザーインターフェース：テンプレート、要件、ガイドライン

本章では、3-D Secure認証を支援するユーザーインターフェース（UI）を構築するための要件、テンプレート例、ガイドラインを示す。

### 4.1 3-D SecureのUIテンプレート

3-D SecureのUIテンプレートは、アプリ方式（NativeまたはHTML）、ブラウザ方式のいずれでも、一貫した利用体験を提供する。イシュアはACSと協力して個別のUI内容を決定し、UIの形式はテンプレートに従う。この一貫性を支援するため、UIのレイアウトを次のゾーンで定義する。

- Headerゾーン（ゾーン1）：3DS Requestorが管理するすべてのラベルを含み、画面上部に配置する。
- Brandingゾーン（ゾーン2）：すべてのロゴを含み、HeaderゾーンとChallengeゾーンの間に配置する。
- Challenge／Processingゾーン（ゾーン3）：処理中の情報とチャレンジ情報を含み、BrandingゾーンとInformationゾーンの間に配置する。
- Informationゾーン（ゾーン4）：カード会員向けの追加情報を含み、画面下部に配置する。

### 4.2 アプリ方式のUIの概要

アプリ方式の実装では、3DS Requestor Appと3DS SDKがUIの描画を制御する。各3DS SDKは、特定の環境（例えば消費者端末のOS）に固有のUI要素を作成する責任を持つ。消費者端末が、次のいずれかのUI形式を決定する。

- Native
- HTML
- NativeとHTMLの両方

注：CReq／CResのやり取りの間、UI形式は一貫したものとすることが望ましい。例えばNative形式で開始した場合、すべてのやり取りでNative形式を維持することが望ましい。

対応するデジタル画像ファイルの種類はpngとjpegである。ACSが実装するその他の画像形式には、3DS SDKが対応しない可能性がある。

注：一部のプラットフォームは、すべての画像形式にネイティブに対応しているとは限らない。

### 4.2.2 Native UIの表示要件

Native UIは、一貫した利用体験を支援するため、3DS Requestor AppのUIに統合される。外観と操作感は3DS Requestor Appと類似し、認証内容はイシュアが提供する。この形式は、イシュアと決済システムのブランド表示も可能にする。

3DS Requestor Appと3DS SDKがUIの描画を制御し、認証ページが3DS RequestorのUIデザイン要素（例えばフォント）を引き継ぐようにする。

3DS SDKによるUI描画処理の詳細は、EMV 3-D Secure SDK—Technical Guideで別途説明する。

UIの内容はイシュアが提供するが、その描画は3DS SDKの責任である。そのため3DS SDKは、消費者端末上で最適に表示されるようUIを調整できる。端末の画面サイズ、向き、フォントサイズなどを把握しているため、イシュアの提供内容を最適化できる（例えば、スクロールの原因となる余分な改行を削除する）。イシュアは、CResで提供した書式が、カード会員に表示されるものと厳密には一致しない場合があることを理解することが望ましい。

### 4.2.2.1 3DS SDK／ACS

3DS SDKは、CReq／CResのやり取りについて次を実施しなければならない。

**Seq 4.19 [Req 362]** ACS UI TypeとApp Screen Orientationについて、表A.20で定義し図4.1および図4.2に示す該当ゾーンと順序で、提供されたすべてのUIデータ要素を表示する。想定される形式は4.2.3節および4.2.6節に示す。

当該ACS UI TypeでサポートしないUIデータ要素を受信した場合、3DS SDKはそれらを表示せず、チャレンジを続行し、ACSにErrorメッセージは送らない。

**Seq 4.20 [Req 398]** 当該ACS UI Typeについて、表A.20で定義する必須のUIデータ要素が欠けている場合、Error Component = C、Error Code = 201のErrorメッセージ（A.9節で定義）をACSに返す。

**Seq 4.21 [Req 363]** ACSがCResで提供した改行を解釈し、画面に配置する。

**Seq 4.22 [Req 364]** Branding、Challenge／Processing、Informationゾーンには、ACSがCResで提供したもの以外のUI要素を表示しない。

**Seq 4.23 [Req 365]** Expandable Information Labelを、展開できるグラフィカルなコントロール（例えばアコーディオン）として表示する。

**Seq 4.24 [Req 366]** カード会員がExpandable Information Labelを選択した場合にのみ、Expandable Information Textを表示する。

**Seq 4.25 [Req 367]** Why Information Labelを、展開できるグラフィカルなコントロール（例えばアコーディオン）として表示する。

**Seq 4.26 [Req 368]** カード会員がWhy Information Labelを選択した場合にのみ、Why Information Textを表示する。

**Seq 4.27 [Req 369]** Cancelアクションを提供する。図4.1および図4.2のとおりHeaderゾーンの上隅にあるボタン、またはプラットフォームのコントローラの機能、もしくはその両方として実装できる。

**Seq 4.28 [Req 392]** Trust List Information Textの既定設定をOffとして表示する。これによりTrust List Data EntryにY値を生成するにはカード会員の操作が必要となる。

**Seq 4.29 [Req 446]** Device Binding Information Textの既定設定をOffとして表示する。これによりDevice Binding Data EntryにY値を生成するにはカード会員の操作が必要となる。

ACSは、CReq／CResのやり取りについて次を実施しなければならない。

**Seq 4.30 [Req 387]** 表A.20で定義する、選択したACS UI TypeでサポートするUIデータ要素のうち、ACSが選択したものだけを含める。

### 4.2.5 HTML UIの表示要件

HTML UIは、HTMLを描画できる消費者端末において、イシュアの一貫したアプリ方式の利用体験をカード会員に提供する。HTML UIテンプレートにより、イシュア固有のデザイン要素（例えばブランド表示、色、フォント）を含めることができる。

3DS SDKは、イシュアが提供したHTMLをそのまま表示する。そのため、消費者端末上で最適に表示されるようHTMLを整形する責任はイシュアにある。3DS SDKがイシュアの提供内容を調整できるNative UIとは異なり、イシュアが提供したHTMLがカード会員に表示される。

HTML UIの実装は、3DS RequestorのWebビューに読み込まれたACS提供のHTML文書と、3DS SDKのプロセス自体との間に、クライアント・サーバ関係を確立する。Webビューが発行するリモートURL要求をインターセプトして3DS SDK内で処理し、消費者端末のOSを経由してインターネットへ送出させないことで実現する。これには次の2つの効果がある。

- Webビュー内で悪意あるHTMLが外部リソースを要求したり、外部の悪意あるサイト（例えばフィッシングページ）へリダイレクトしたりすることを防ぐ。
- Webビューのフォームを、3DS SDKのUIの拡張にする。その内容は3DS SDKや3DS Requestor Appではなく、リモートのACSがHTMLで定義する。

HTML UIにおける主な考慮事項：

- Webビューの内容は、レスポンシブHTMLとしてACSから直接受信し、3DS SDKがWebビュー内に表示する。Webビュー内からの画面遷移の試みは、OSやネットワークスタックへ渡さず、3DS SDKが捕捉して内部処理する。画面遷移に加え、外部リソース要求（画像の読込み、外部JSスクリプト、CSSなど）も捕捉する。
- Webビュー要素はブラウザとしてではなく、ACSが提供するHTMLとCascading Style Sheets（CSS）を内容とするUI要素として使用する。
- すべてのネットワーク通信をルーティングするため、消費者端末とACSの間にセキュアな通信経路を確立する。Webビューとのすべての対話を3DS SDKによるものとして定義することで、UIを定義・所有するのは3DS SDKであり、3DS Requestor Appはチャレンジの対話から隔離されることを明確にする。

## 原本 144ページ

### 4.4 3RIの考慮事項

2種類の3RI取引では、UIの考慮事項が異なる。

第1の種類は、主に継続課金取引であり、3DS Requestorが、サブスクリプションの利用者が引き続き有効な支払手段を持っているかを確認するものである。カード会員がその場にいないため、この種類の3RI取引ではUIを提示しない。

第2の種類は、例えばMOTO取引のように、3DS Requestorがカード会員を認証する方法としてDecoupled Authenticationを要求するものである。ACSがDecoupled Authentication用に提供するUIは、EMV 3-D Secureプロトコルの対象外である。

3DS Requestorは、AReq／ARes処理中に処理中画面を表示でき、ACSがAResでCardholder Information Textを提供した場合には、その要素を伝えることができる。固定電話やフィーチャーフォンを通じたMOTO取引では、3DS Requestorの顧客サービス担当者が、Cardholder Information Textを口頭で伝えることができる。
