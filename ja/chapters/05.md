## 5 EMV 3-D Secureのメッセージ処理要件

本章では、接続の確立、メッセージの解析・検証、メッセージ処理、エラー処理など、3-D Secureのメッセージ処理機能を詳述する。すべてのフローの3-D Secureメッセージは、ドメイン間の相互運用性を向上させるため、公開されたインターネット標準を使用する。本章でそれらの標準を参照する。

### 5.1 一般的なメッセージ処理

### 5.1.1 HTTP POST

相互運用性を確保するため、すべての3DS構成要素は、HTTP POSTについて次の方法に従わなければならない。

**Seq 5.1 [Req 184]** すべての3-D Secureメッセージ要求は、6.1節で定義する保護された接続を通じ、RFC 7231で定義するHTTP POSTで送信しなければならない。

**Seq 5.2 [Req 185]** 3-D Secure構成要素間で交換するメッセージは、RFC 7159で定義するJSONデータ交換形式、またはRFC 7516／RFC 7515で定義するJWE／JWSオブジェクト形式でなければならない。

**Seq 5.3 [Req 186]** HTTPメッセージの本文は、RFC 7159で定義するJSON必須のUTF-8文字集合を使って正しく整形されたJSONメッセージ、またはRFC 7516／RFC 7515で定義するJWE／JWSオブジェクト形式を含まなければならない。メッセージに含められる内容を最大化するため、JSONデータの引用符で囲まれた文字列の外にある空白文字（スペース、復帰、改行など）を削除することを推奨する。

**Seq 5.4 [Req 187]** 接続にはHypertext Transfer ProtocolのHTTP/1.1以上を使用しなければならない。HTTP/1.1の詳細はRFC 2616を参照すること。

**Seq 5.5 [Req 188]** チャンク転送符号化を使用しない場合、Content-Lengthヘッダーを含め、メッセージ本文の長さを設定しなければならない。HTTP/1.1のチャンク転送符号化の詳細はRFC 2616を参照すること。

**Seq 5.6 [Req 189]** 応答は5.1.2節に従って整形し（形式とContent-Typeヘッダーを含む）、HTTP POSTへの返信として送信しなければならない。

**Seq 5.7 [Req 313]** 3-D Secure構成要素間で交換する暗号鍵は、RFC 7517で定義するJWKオブジェクト形式でなければならない。

### 5.1.2 HTTPヘッダー：Content-Type

3-D SecureメッセージのHTTPヘッダーは、受信側がメッセージ本文の内容を正しく処理できるよう、その内容を伝える。3-D SecureはHTTPヘッダー、特にRFC 2616で定義するContent-Typeヘッダーフィールドを使用する。

**Seq 5.8 [Req 190]** 次のメッセージのHTTPヘッダーには、Content-Typeとして`application/JSON`を含め、charsetとしてUTF-8を含めなければならない。

- AReq／ARes

**Seq 5.9 [Req 191]** CReq／CResのContent-Typeヘッダー要件は次のとおりである。

- アプリ方式のCReq／CRes：Content-Typeに`application/jose`を含め、charsetとしてUTF-8を含めなければならない。例：`Content-Type: application/jose; charset = UTF-8`。

**Seq 5.10 [Req 468]** AReq、CReq、RReq、OReq、PReqでは、送信する3DS構成要素は、表A.29で定義するとおり、HTTPヘッダーのX-Request-IDを使って自身のTransaction IDを含めなければならない。

**Seq 5.11 [Req 469]** ARes、CRes、RRes、ORes、PResでは、送信する3DS構成要素は、表A.29で定義するとおり、X-Response-IDを使って自身のTransaction IDを含め、X-Request-IDを使って要求メッセージ内（HTTPヘッダー内ではない）で受信した送信元のTransaction IDを含めなければならない。

### 5.1.3 Base64／Base64urlエンコード

3-D Secure仕様では、附属書Aで定義する特定のメッセージ要素の内容の整形に一貫性を持たせるため、Base64およびBase64urlエンコードを使用する。

**Seq 5.12 [Req 192]** エンコード方法は、Base64についてIETF RFC 2045、Base64urlについてIETF RFC 7515に従わなければならない。

**Seq 5.13 [Req 193]** Base64復号ソフトウェアは、Base64でエンコードされたデータ内の空白文字（復帰や行末など）を無視し、それらの存在をエラーとして扱ってはならない。

### 5.1.4 プロトコルとメッセージのバージョン番号

注：Protocol Version NumberおよびMessage Version Numberは、major.minor.patch形式（例えば2.3.1）である。

**Seq 5.14 [Req 195]** EMV Specification Bulletin 255で有効とされていないMessage Version Numberは、すべてエラーとして返さなければならない。3-D Secure構成要素は、適切なError ComponentとError Code = 102を持つErrorメッセージ（A.9節で定義）を返さなければならない。

**Seq 5.15 [Req 320]** Message Version Numberは、3DSメッセージを開始する3-D Secure構成要素が設定する。各3-D Secure構成要素は、3-D Secure取引を通じてその値が変わらないことを検証しなければならない。検証エラーを特定した構成要素は、適切なError ComponentとError Code = 203を持つErrorメッセージ（A.9節で定義）を返さなければならない。

**Seq 5.16 [Req 396]** 3DS SDKは、3DS SDK Device Informationの最新のData Versionに対応しなければならない。

**Seq 5.17 [Req 397]** ACSは、3DS SDK Device Informationのすべての有効なData Versionに対応しなければならない。

注：EMV Specification Bulletin 255およびEMV 3-D Secure SDK—Device Informationを参照すること。

### 5.1.6 メッセージの解析

3-D Secureメッセージの受信側は、正しく処理できることを確実にするためメッセージを検証する。受信時に、次を検証しなければならない。

**Seq 5.18 [Req 196]** 附属書Aで定義する適用要件を満たすこと。

**Seq 5.19 [Req 197]** Message Typeフィールドに基づき、取引のコンテキストが受信側構成要素にとって有効であること。

**Seq 5.20 [Req 198]** RFC 7159で定義するJSONメッセージ、またはRFC 7516／7515で定義するJWE／JWSオブジェクト形式として正しく整形されていること。

**Seq 5.21 [Req 199]** Message Typeフィールドが受信側構成要素にとって有効であること。

受信側構成要素は、次のメッセージ種別を受信する。

**Seq 5.22 [Req 200]** 3DS SDKは、CResまたはErrorメッセージのみを受け付けなければならない。他の種別はエラーとして扱わなければならない。

**Seq 5.23 [Req 201]** 3DS Serverは、ARes、RReq、PRes、OReq、Errorメッセージのみを受け付けなければならない。他の種別はエラーとして扱わなければならない。

**Seq 5.24 [Req 202]** DSは、AReq、ARes、RReq、RRes、PReq、ORes、Errorメッセージのみを受け付けなければならない。他の種別はエラーとして扱わなければならない。

**Seq 5.25 [Req 203]** ACSは、AReq、CReq、RRes、OReq、Errorメッセージのみを受け付けなければならない。他の種別はエラーとして扱わなければならない。

**Seq 5.26 [Req 430]** 3DS Serverが1つの取引中に複数のRReqを受信した場合、Error Code = 312を返さなければならない。

### 5.1.7 メッセージ内容の検証

メッセージの検証時には、次の要件を適用する。

**Seq 5.30 [Req 204]** 表A.1で定義するとおり、受信したMessage TypeのすべてのRequiredフィールドが存在しなければならない。

**Seq 5.31 [Req 205]** 表A.1で定義する存在条件を送信元構成要素が満たすと判断した場合、受信したMessage TypeのすべてのConditionalフィールドが存在しなければならない。

**Seq 5.32 [Req 206]** Message Typeに含まれるRequired、Conditional、Optionalフィールドは、表A.1で指定する形式と長さの基準を満たさなければならない。

**Seq 5.33 [Req 309]** 明示的な注記がない限り、条件付き任意または任意のフィールドが空またはnullとして送信された場合、受信側は、適切なError ComponentとError Code = 203を持つErrorメッセージ（A.9節で定義）を返さなければならない。

例：DSがACSから、Message Type、Device Channel、Message Categoryについて表A.1で指定されているが条件を満たさない、空の条件付き任意データ要素を持つAResを受信する。例えば`acsChallengeMandated = ""`かつ`transStatus = Y`の場合である。DSはAResの内容を検証し、ACSにエラーを返す。3DS ServerにはAResまたはErrorを返すことができる。

メッセージの検証基準はMessage Typeフィールドに基づき、次のとおり適用する。

**Seq 5.34 [Req 207]** 将来のプロトコルバージョンに対応するため、実装は厳格な検証を行うJSON内容パーサを使用、またはそのように設定してはならない。構文が正しく、表A.1で定義するMessage Typeの検証基準を満たす場合、メッセージを有効とみなさなければならない。

**Seq 5.35 [Req 208]** 受信したMessage Typeの内容検証が、表A.1の基準を満たさない場合、エラーとして扱わなければならない。

**Seq 5.36 [Req 209]** Message Type、Device Channel、Message Categoryについて指定されていない追加データ要素を受信しても、それ以外の検証に合格する場合、メッセージを有効とみなさなければならない。

追加データ要素（データ拡張を除く）について、受信側3DS構成要素は次のいずれかを実施しなければならない。

- 追加データ要素を無視し、フロー内の次の3DS構成要素へ送らない。
- 次ページに示す形式確認を行う。

内容検証の要件：

**Seq 5.39 [Req 212]** 3-D Secure構成要素は、Transaction IDとReference Numberを含む、表A.1で定義する応答メッセージのデータ要素が、対応する要求メッセージと一致することを確実にしなければならない。

### 5.2 部分的なシステム停止

3-D Secure構成要素は、実質的に稼働できなくなるシステム障害に遭遇する場合がある。

**Seq 5.41 [Req 215]** システム障害を検出した場合、修復されるまで要求の受付を停止しなければならない。処理中のすべての要求について、適切なError ComponentとError Code = 403または404を持つErrorメッセージ（A.9節で定義）を送信しなければならない。

### 5.3 3-D Secure構成要素の可用性

3-D Secureエコシステム全体の健全性を維持するため、すべての構成要素について、ソフトウェア、システム、インフラストラクチャの設計で高可用性を主要な要素として構成することを推奨する。追加の推奨事項は次のとおりである。

- ある構成要素の可用性を、メッセージのルーティングや負荷分散を処理する他の構成要素に依存させないことが望ましい。
- ルーティング目的で複数のURLを任意に保存してもよいが、それだけを高可用性の解決策としないことが望ましい。

注：高可用性のベストプラクティスの詳細は、EMV 3-D Secureの対象外である。

### 5.4 エラーコード

**Seq 5.42 [Req 216]** すべての3-D Secure構成要素は、Error Codeフィールドのあらゆる値を受け付けなければならない。

**Seq 5.43 [Req 217]** 表A.4のError Code一覧に、検出した状況と一致する項目がない場合、合理的に近いものを使用しなければならない。

**Seq 5.44 [Req 218]** Error Code 201、203、204、304では、エラーを特定した構成要素は、不正なデータ要素の名前をError Detailに含めなければならない。

### 5.5.2 読取りタイムアウト

構成要素間でメッセージを適時に処理するため、すべての構成要素は実装（プログラミング言語の関数、インフラストラクチャの構成要素など）に適した読取りタイムアウトを設定する。

読取りタイムアウトは、接続確立後にメッセージを送信し、取引の応答を待つ間に発生する。接続タイムアウトは、最初の接続（TCP/IP接続とTLSハンドシェイクの完了）を行う間に発生する。

注：読取りタイムアウト値は各DSの実装が定義し、DSごとに異なる場合がある。

### 5.5.2.1 AReq／AResのタイムアウト

AReq／AResの読取りタイムアウトは次のとおり処理する。

**Seq 5.59 [Req 228]** 3DS ServerとACSは、各DSとの個別の通信について、DS要件が定める適切なAReq／AResのタイムアウト値を設定しなければならない。

### 5.11 OReq／OResのメッセージ処理要件

Operationメッセージにより、DSは3DS ServerまたはACSに運用情報を伝えられる。支払／非支払認証取引から独立していても、関連していてもよい。EMV 3DSプログラム全体のシステムの健全性や管理に関する情報を伝えるために使用できる。例えば次の用途がある。

- 処理所要時間と性能の報告。
- エコシステム内の不正な参加者の検出と警告。
- 鍵交換・証明書更新・リマインダーのDSからの通知。

Operationメッセージを使用するDSは、次を実施しなければならない。
