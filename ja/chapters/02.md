## 2 EMV 3-D Secureの概要

この概要では、3-D Secureの実装に必要な構成要素、システム、および機能を説明する。説明は、次のドメインに分けている。

- アクワイアラ・ドメイン：3-D Secure取引を開始する。
- 相互運用ドメイン：アクワイアラ・ドメインとイシュア・ドメイン間で3-D Secure取引を中継する。
- イシュア・ドメイン：3-D Secure取引の認証を行う。

図2.1は、3つのドメインの相互作用と、各ドメインの構成要素を示している。3DS Requestor Environmentの実装はさまざまであるため、この図は、これらの構成要素の具体的な実装や相互運用方法を意図的に限定していない。例えば、3DS Clientは3DS Serverと直接通信してもよく、3DS Serverと3DS Requestorの機能を統合してもよい。

## 原本 36ページ

### 2.1 アクワイアラ・ドメイン

アクワイアラ・ドメインは、次の構成要素を持つ。

- 3DS Requestor Environment（3DS Requestor、3DS Client、3DS Server）
- 3DS Integrator
- アクワイアラ（支払オーソリゼーション用）

### 2.1.1 3DS Requestor Environment

3DS Requestor Environmentは、3DS Requestorの管理下で3-D Secureを支援する構成要素の総称である。次の構成要素を含む。

- 3DS Requestor
- 3DS Client
- 3DS Server

### 2.1.1.1 3DS Requestor

3DS RequestorはAReqメッセージを開始し、消費者端末からの3-D Secureデータを受け渡す。例えば支払認証では、通常、オンラインショッピング用の既存の加盟店Webサーバが3DS Requestorに相当する。3DS Requestorは、消費者端末上の3DS Requestor App、または3DS Method／ブラウザを介して3DS Clientと連携する。また、3DS Serverに接続するか、3DS Serverと統合される。3-D Secure取引を処理する方法は次のとおりである。

- アプリ方式：適用される3DS SDK仕様に従って、3DS Requestor Appに3DS SDKを組み込む。3DS SDKはカード会員にユーザーインターフェース（UI）を表示する。
- ブラウザ方式：3DS Requestorのブラウザ方式のソリューションは、3DS Methodを使用してブラウザ情報／端末の詳細を収集する。チャレンジが必要な場合、ACSがブラウザにHTMLを提供し、カード会員にUIを表示する。

### 2.1.1.2 3DS Client

3DS Clientは、消費者端末上で3-D Secure認証を開始する構成要素である。例えば支払認証では、オンラインショッピングの一環として加盟店のチェックアウトに組み込まれる。次の2つのモデルで実装できる。

- アプリ方式：3DS Clientは、3DS Requestor Appに組み込まれ、カード会員との対話を支援する3DS SDKである。3DS SDKは、消費者端末から3-D Secure情報を収集し、Access Control Server（ACS）の認証を支援し、カード会員の認証データの流れを保護する。
- ブラウザ方式：3DS Clientは、3DS RequestorのWebサイトに組み込まれ、消費者端末のブラウザ内で呼び出される3DS Methodである。

## 原本 37ページ

3DS Methodは、3DS Integratorが提供するスクリプト呼出しであり、支払取引における加盟店のチェックアウトページなど、カード会員が操作するWebサイトに配置される。その目的は、リスクに基づく判断を支援するために、追加のブラウザ情報を取得することである。

### 2.1.1.3 3DS Server

3DS Serverは、3DS Requestor Environment内の処理フローとDSの間に、機能上のインターフェースを提供する。次の責任を持つ。

- 3-D Secureメッセージに必要なデータ要素を収集する。
- DSを認証する。
- DS、3DS SDK、および3DS Requestorを検証する。
- メッセージ内容の保護を確実にする。

3-D Secure認証を開始するため、3DS Serverは、3DS Requestor Environment内の任意の構成要素、またはすべての構成要素から必要なデータ要素を収集する。例えば支払認証では、カード会員が消費者端末を使ってアカウント情報を提供してもよく、3DS Requestor Environment内で情報を保管していてもよい。端末情報は3DS Clientが取得し、3DS Serverに転送する。

注：支払認証の後、3DS Requestorの構成によっては、3DS Serverがアクワイアラにも接続し、オーソリゼーション要求を開始することがある。

### 2.1.2 3DS Integrator（3DS Serverおよび3DS Client）

3DS Integratorは、3DS Requestor Environmentと3-D Secureメッセージの間に機能上のインターフェースを提供する。その役割は、3DS Serverと3DS Clientを提供し、3-D Secure機能を3DS Requestorの業務機能に統合することである。この機能は、認証メッセージのやり取りでDSおよびACSと接続するうえで不可欠であり、チャレンジが実施された場合には、その結果の受渡しも担う。

3DS Integratorは、承認済みの3DS SDK構成要素または3DS Method機能を3DS Requestorに提供し、その3DS Requestor AppやWebサイトへの組込みを可能にする。必要なすべてのDSへの加盟店登録に責任を持つ。

注：支払認証の後、3DS Integratorは、アクワイアラとのオーソリゼーション機能を提供できる。

### 2.1.3 アクワイアラ（支払オーソリゼーション）

アクワイアラは、次の役割を持つ金融機関である。

- 決済カード取引を受け付ける目的で、加盟店と契約関係を結ぶ。
- 加盟店の3-D Secureへの参加を支援する。

## 原本 38ページ

3-D Secureによる支払認証の後、アクワイアラは次の従来の役割を果たす。

- 加盟店からオーソリゼーション要求を受け取る。
- オーソリゼーション・システムにオーソリゼーション要求を送る。
- 加盟店にオーソリゼーション応答を提供する。
- 完了した取引を決済システムに提出する。

### 2.2 相互運用ドメイン

相互運用ドメインは、次の構成要素を持つ。

- Directory Server（DS）
- Directory Server Certificate Authority（DS CA）
- オーソリゼーション・システム

### 2.2.1 Directory Server

DSは、次の機能などを実行する。

- 3DS ServerおよびACSを認証する。
- 3DS ServerとACSの間でメッセージをルーティングする。
- 3DS Server、3DS SDK、および3DS Requestorを検証する。
- 個別のプログラム規則（例えば、ロゴ、タイムアウト値など）を定める。
- 3DS ServerおよびACSの導入・登録を行う。
- ACSおよびDSのプロトコルバージョン一覧と、3DS Method URLを管理する。

### 2.2.2 Directory Server Certificate Authority

DS CAは、3DS SDK向けのDS公開鍵を生成し、3-D Secure構成要素が使用するTransport Layer Security（TLS）証明書を生成する。通常、特定のDSを担当する決済システムが運営する。証明書には次のものが含まれる。

- 3DS ServerとDSの間、およびDSとACSの間の通信に使用するTLSクライアント証明書とサーバ証明書。
- ACSから3DS SDKに渡されるデータ要素への署名に使用する証明書。
- 3DS SDKからDSに渡されるデータ要素への署名に使用する証明書。

証明書の詳細については第6章を参照すること。

### 2.2.3 オーソリゼーション・システム（支払認証）

オーソリゼーション・システムは、支払認証の後、次の従来の役割を果たす。

- アクワイアラからオーソリゼーション要求を受け取る。
- イシュアにオーソリゼーション要求を送る。
- アクワイアラにオーソリゼーション応答を提供する。
- アクワイアラとイシュアに清算・決済サービスを提供する。

### 2.3 イシュア・ドメイン

イシュア・ドメインは、次の構成要素を持つ。

- カード会員
- 消費者端末
- イシュア
- Access Control Server（ACS）

### 2.3.1 カード会員

カード会員は、消費者端末を使ってアカウント情報を提供する。必要な場合は、認証のための追加情報の提供を求められる。

### 2.3.2 消費者端末

消費者端末は、3DS Requestor Appを実行するか、ブラウザ上にWebサイトを表示し、3-D Secure認証に利用できる。3DS Requestor Environmentの消費者端末側の構成要素は、モデルによって異なる。

- アプリ方式：3DS Requestor Appに組み込まれた3DS SDK。
- ブラウザ方式：3DS Methodを使用するブラウザ。

これらの構成要素は、3DS Requestorおよび3DS Serverと所定の関係を持つ。

### 2.3.3 イシュア

イシュアは、次の役割を持つ金融機関である。

- 1枚以上の決済カードを発行するため、カード会員と契約関係を結ぶ。
- 3-D Secureへの参加対象となるカード番号の範囲を定義する。
- 該当するDSに追加するカード番号の範囲を提供する。

### 2.3.4 Access Control Server

ACSは認証規則を保持し、イシュアによって管理される。次の機能を含む。

- カード番号が3-D Secure認証の対象かを検証する。
- 消費者端末の種類が3-D Secure認証の対象かを検証する。
- カード会員を認証するか、アカウント情報を確認する。

これらの機能は単一の論理的なACSに属する場合があるが、実装によっては、機能やその他の特徴（例えばカード番号範囲）に応じて、複数の物理サーバに処理を分散できる。

### 2.4 3-D Secureメッセージ

本節では、3-D Secureで定義されるメッセージを紹介する。メッセージ処理の詳細は第5章、メッセージのデータ要素は附属書Bを参照すること。

### 2.4.1 Authentication Requestメッセージ（AReq）

AReqは、3-D Secure認証フローの最初のメッセージである。3DS Serverは、カード会員の認証を要求する際にAReqを生成する。取引に関するカード会員情報、支払情報、端末情報を含めることができる。認証ごとにAReqは1つのみである。ただし、3DS Requestor主導のSPC認証と、Decoupled Authentication Fallbackを除く。

### 2.4.2 Authentication Responseメッセージ（ARes）

AResは、AReqに対するイシュアのACSからの応答である。カード会員が認証されたこと、または認証を完了するためにカード会員との追加の対話が必要なことを示すことができる。認証ごとにAResは1つのみである。ただし、3DS Requestor主導のSPC認証と、Decoupled Authentication Fallbackを除く。

### 2.4.3 Challenge Requestメッセージ（CReq）

CReqは、チャレンジフローにおけるカード会員との対話を開始する。また、カード会員からの認証データを運ぶために使用できる。

- アプリ方式：3DS SDKがCReqを送信する。認証を完了するためにACSとカード会員の間で複数回のやり取りが必要になる場合があるため、チャレンジごとに2つ以上のCReqがある。
- ブラウザ方式：3DS ServerがCReqを生成し、カード会員のブラウザを通じてPOSTする。チャレンジごとにCReqは1つのみである。

### 2.4.4 Challenge Responseメッセージ（CRes）

CResは、CReqに対するACSからの応答である。カード会員認証の結果を示すことができる。アプリ方式では、認証を完了するためにカード会員との追加の対話が必要なことも示せる。

- アプリ方式：CResのデータ要素は、3DS SDKがチャレンジ用UIを生成・表示するために必要なデータを提供する。カード会員認証を完了するために、取引ごとに2つ以上のCResがある。
- ブラウザ方式：CResは認証結果を含み、カード会員のチャレンジを完了する。チャレンジごとにCResは1つのみである。

### 2.4.5 Results Requestメッセージ（RReq）

RReqは、認証または検証の結果を伝える。ACSからDSを経由して3DS Serverに送信される。3DS取引ごとにRReqは1つのみである。フリクションレス取引ではRReqは存在しない。

### 2.4.6 Results Responseメッセージ（RRes）

RResは、RReqの受信を確認する。3DS ServerからDSを経由してACSに送信される。RReqごとにRResは1つのみである。

### 2.4.7 Preparation Requestメッセージ（PReq）

PReqは、ACSおよびDSに関する情報を要求するため、3DS ServerからDSに送信される。このメッセージは3-D Secure認証メッセージフローの一部ではない。

### 2.4.8 Preparation Responseメッセージ（PRes）

PResは、PReqに対するDSからの応答である。3DS Serverは、PResを利用してACSおよびDSの情報（例えば対応するプロトコルバージョン）をキャッシュできる。このメッセージは3-D Secure認証メッセージフローの一部ではない。

### 2.4.9 Operation Requestメッセージ（OReq）

OReqのメッセージシーケンスは、警告、通知、報告、または対応の要請として、運用情報を伝えるために生成される。このメッセージは3-D Secure認証メッセージフローの一部ではない。

### 2.4.10 Operation Responseメッセージ（ORes）

OResは、OReqのメッセージシーケンスの受信を確認する。OReqのメッセージシーケンスの受信側が生成し、OReqの送信元に送る。

### 2.4.11 Errorメッセージ

Errorメッセージは、3DS Server、DS、ACS、および3DS SDKの間でメッセージを処理する際に発生したエラーの追加情報を提供する。詳細は第5章、附属書A、および附属書Bを参照すること。

### 2.5 認証フロー

本節では、EMV 3-D Secureで定義される認証フローを紹介する。認証フローの要件は、本仕様の第3章を参照すること。

### 2.5.1 フリクションレスフロー

フリクションレスフローは3-D Secure認証フローを開始し、AReqとAResで構成される。認証を成功させ、3-D Secure認証処理を完了するために、カード会員との追加の対話を必要としない。

### 2.5.2 チャレンジフロー

チャレンジフローは、フリクションレスフローを構成するAReqとAResに加え、RReqとRResによって完了する。また、Decoupled Authenticationの場合を除き、CReqとCResを含む。認証を完了するためにカード会員との追加の対話が必要だとACSが判断した場合、フリクションレスフローからチャレンジフローに移行する。

例えば、取引のリスクが高いと判断された場合、所定のしきい値を超えた場合、または各国の義務（もしくは規制）により高い認証水準が必要な場合に、チャレンジが必要になることがある。3DS Requestorは、チャレンジを続行するか、3-D Secure認証処理を終了するかを決定する。

### 2.5.3 EMV Payment Tokenの処理

一般的な構成：EMV Payment Tokenで開始するフローを本仕様に従って適切に処理するため、Payment Tokenの範囲を共有し、該当するDSに設定しなければならない。これは、EMV Payment Token取引を適切なDS、続いてACSにルーティングするために不可欠である。

取引フロー中のEMV Payment Tokenの処理：Authentication Request（AReq）のメッセージフロー中に、Payment Tokenを非トークン化し、以降のAReqフローのCardholder Account Numberに実際のPANを設定する必要が生じる場合がある。例えば、EMV Payment Tokenで取引が開始され、ACSがPANに基づいて設定されている場合が該当する。この場合、AReqのEMV Payment Token IndicatorをTrueに設定し、EMV Payment Tokenで取引が開始されたことを示す。

### 2.6 フリクションレスフローの概要

開始：カード会員が、消費者端末上で取引を開始する。認証に必要な情報を提供する（カード会員が入力するか、加盟店に既に登録されている情報を使用する）。

1. 3DS Requestor Environment：必要な3-D Secure情報を環境内で収集し、AReqに含めるため3DS Serverに渡す。

どのように、またどの構成要素から情報を提供するかは、次の条件に依存する。

- Device Channel：アプリ方式（2.6.1節）またはブラウザ方式（2.6.2節）。
- Message Category：PaymentまたはNon-Payment。
- 3DS Requestorの3-D Secure実装（2.1.1節）。

2. 3DS ServerからDSを経由してACSへ：カード会員が提供した情報と3DS Requestor Environment内で収集したデータを使い、3DS ServerがAReqを生成してDSに送信する。DSは適切なACSに転送する。

3. ACSからDSを経由して3DS Serverへ：AReqへの応答として、ACSがAResをDSに返す。DSは開始元の3DS Serverに転送する。

応答を返す前に、ACSはAReqで提供されたデータを評価する。フリクションレスフローでは、認証を完了するためのカード会員との追加の対話は不要だと判断する。

4. 3DS Requestor Environment：3DS ServerがAResの結果を3DS Requestor Environmentに伝え、同環境がカード会員に通知する。

2.1.1節に定めるとおり、これらの構成要素間の対話の実装方法は3DS Requestorが決定する。詳細は2.6.1節および2.6.2節を参照すること。

注：3-D Secure処理はここで終了する。支払オーソリゼーションには、次の手順が適用される。

5. 加盟店とアクワイアラ：加盟店がアクワイアラとのオーソリゼーションのやり取りに進む。該当する場合、加盟店、アクワイアラ、またはPayment Processorは、標準のオーソリゼーション要求を送信できる。

6. 支払オーソリゼーション：アクワイアラは、決済システムを通じてイシュアとオーソリゼーションを処理し、その結果を加盟店に返すことができる。

### 2.6.2 3DS Requestor Environment―ブラウザ方式

ブラウザ方式では、TLSを使用するブラウザ接続を通じ、消費者端末と3DS Server／3DS Requestorの間で通信する。図2.4は3DS Requestor Environmentを示す。

![図2.4：3DS Requestor Environment―ブラウザ方式](../../assets/images/figure-2-4.png)

手順1および4の機能は2.6節で定義されており、次の補足がある。

開始：カード会員が、消費者端末のブラウザから3DS Requestorが運営するWebサイトを利用して、取引を開始する。

1.1 3DS Requestorと3DS Server：3DS Requestorが3DS Serverと通信する。3DS Serverは、要求されたカード範囲に対するACSおよびDSのプロトコルバージョンを判定し、3DS Method URLがある場合は取得して、情報を3DS Requestorに返す。ACSおよびDSのプロトコルバージョンと3DS Method URLのデータは、3DS Serverが以前にPResを通じて受信したものである。

1.2 3DS Requestorのチェックアウトページ上の3DS Method：3DS Method URLがある場合、3DS RequestorのチェックアウトページがそのURLを読み込む。これによりACSは、リスクに基づく判断のために追加のブラウザ情報を取得できる。

1.3 3DS Requestorと3DS Server：3DS Requestorが、取引に必要な3-D Secure情報を3DS Serverに提供する。

4. 3DS Serverと3DS Requestor：3DS ServerがAResの結果を3DS Requestorに伝え、取引を完了する。構成要素間の対話の実装方法は3DS Integratorが決定する。
