## 原本 49ページ

## 3 EMV 3-D Secure認証フローの要件

本章では、EMV 3-D Secure処理フローの要件を定める。明確化のため、3-D Secure認証処理に関与するすべての構成要素の動作を説明するが、本コア仕様が対象とするのは次の4つである。

- 3DS Client（3DS SDK、3DS Method）
- 3DS Server
- Directory Server（DS）
- Access Control Server（ACS）

各構成要素は、記載どおりに仕様に従わなければならない。アプリ方式のモデルについては、詳細な要件と実装ガイドラインを定める、適用される3DS SDK仕様も参照すること。

第2章で紹介したとおり、チャレンジフローの初期処理はフリクションレスフローと同じである。そのため本章では、両方のフローを1つの処理フローとして説明する。

注：本章を通じて使用する「検証（Validate）」は、3-D Secure構成要素が受信メッセージを検証する要件を指す。実際の検証処理の詳細は5.9節の該当する小節で定義する。検証処理には、表A.1のデータ要素と5.1.6節の機能に基づく、各データ要素の有無および形式の確認が含まれ、メッセージにエラーがある場合の実際のエラー処理も含まれる。また、メッセージの暗号学的検証や復号を含めてもよい。

## 原本 51ページ

#### 手順1：カード会員

カード会員は、3DS Requestor Appを使って3DS Requestorと対話し、該当する業務ロジックを確認する。例えば、消費者端末上の3DS Requestor Appを使って電子商取引による購入を行う。

#### 手順2：3DS Requestor App

3DS Requestor Environment（2.1.1節で概説）によっては、追加情報を取得してもよい。例えば、支払認証のための支払情報やショッピングカート情報が該当する。

3DS Serverは、3DS Requestor Environmentを通じて、次の情報を3DS Requestor Appに提供する。

- 端末情報の暗号化に使う鍵を識別するDirectory Server ID値（決済システムのRID）。
- CReq／CResで使用するMessage Version Number。

3DS Serverは、次を実施しなければならない。

**Seq 3.1 [Req 11]** ISO 7812で定義されるBINと、任意のその他のCardholder Account Informationに基づき、認証取引の送信先となるDSを判定する。

**Seq 3.2 [Req 419]** PResから取得したACS Protocol VersionsおよびDS Protocol Versionsのプロトコルバージョン一覧と、3DS SDKが対応するプロトコルバージョンを使い、共通して対応する最高のMessage Version Numberを設定する。

3DS Requestor Appは、3-D Secureカード会員認証を開始するために3DS SDKを起動する。次の情報を3DS SDKに渡す。

- Directory Server ID値（決済システムのRID）。
- Message Version（3DS Requestor Environmentから取得）。

また、次の情報を取得する。

- SDK Transaction ID
- SDK App ID
- Device Information
- Protocol Version（この取引で3DS SDKが使用するバージョン）

注：Message Versionがnullの場合、3DS SDKは対応する最高のプロトコルバージョンを使用する。値がある場合はそのバージョンを使用する（3DS SDKが対応していることが前提）。対応していなければエラーとなる。

注：適用される3DS SDK仕様に記載するとおり、3DS SDKはDS公開鍵を使ってDevice Informationを暗号化する。この鍵は、3DS SDKの起動時に渡されるDirectory Server IDに基づいて識別される。

#### 手順3：3DS SDK

3DS SDKは、AReqに必要なデータを返す。

#### 手順4：3DS Requestor Environment

3DS Requestor Environmentは、3DS Serverが組み立てるAReqの情報を収集する責任を持つ。

### 3.5 SPC方式の認証要件

SPC（Secure Payment Confirmation）は、ブラウザ使用時に、事前に確立されたFIDOクレデンシャルを使ってチャレンジを実施する方法を提供する。SPC認証は、追加のAReq／AResの組を使って3DS Requestorが開始するか、標準のブラウザ・チャレンジフローを使ってACSが開始できる。

本節では、SPCをチャレンジ方法として使用する2つの方式について、通常のブラウザフロー（3.3節）との違いを概説する。SPC認証を正しく実行するため、次の前提条件が適用される。

1. ACSが、このカード会員の端末上のFIDO Authenticatorを登録済みである。
2. 3DS RequestorまたはACS、もしくはその両方が、カード会員のブラウザが関連するSPC API（`allow="payment *; publickey-credentials-get *"`）に対応していることを検出している。ACSは、Browser User Agentデータ要素、または3DS Methodで取得したデータを通じてこの情報を取得できる。

注：DSがFIDO Relying Partyとして動作し、SPCフロー内でACSについて記載する動作の一部またはすべてを実施してもよい。

### 3.5.1 3DS RequestorがSPC認証を開始する場合

3DS Requestorが開始するSPC認証フローの手順は、標準のブラウザフロー（図3.3で概説）に、9つの追加手順（図3.5の手順10a〜10i）を加えたものである。SPC認証の影響を受けない手順を含め、フロー全体を図3.5に示す。
